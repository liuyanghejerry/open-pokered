# 训练家只登记实际派出的宝可梦

复刻在 `start_trainer_battle` 读取训练家队伍时，把整队全部登记为“见过”。因此在 3 号道路首只小拉达处战败，也会登记尚未出场的阿柏蛇。

原作 `engine/battle/core.asm:5992–5996,6130–6140` 在 `LoadEnemyMonData` 加载当前敌人时登记 `wEnemyMonSpecies2`；通信战斗提前跳到 `LoadEnemyMonFromParty`，不执行这次登记。本修复由真正的首次加载、昏倒替补及 TrainerAI 换人产生待处理位置位，前端只消费这些加载通知。队伍始终由 `BattleState.enemy` 单独持有；通知不复制宝可梦，稳定帧也不读取活动位置或重复写图鉴。同帧加载多个位置会全部保留，`party_mon` 保留变身前身份；野生与通信路径消费通知后不新增 seen。

## 回归与边界

- 最终 debug-server 与默认特性应用专项各 **9通过**；完整应用 **289通过、39忽略、0失败**，完整核心 **2887通过**，快照确定性集成 **8通过**，显式 debug-server 应用构建通过。
- 回归覆盖首只登记、连续多场首个 slot0、真实 `post_text_transition` 派出后续敌人、Juggler 实际 AI 从0换1再换0且双方仍存活、Transform 原始身份、通信与野生排除、普通读档和软重置清理、两个运行时快照恢复入口，以及同帧多个加载通知的 JSON 往返。
- 新快照显式保存通知位，包括 `Some(0)`；只有字段缺失的旧快照才补当前实际位置的一次通知。此区别保留新快照原样恢复，避免把已经消费的加载重新排队。
- 通信及 Transform 只做了单元/静态检查，没有冒充实际双端通信或实际 Ditto 对照。野生幽灵的登记差异不在本修复中。
- 只验证 Red 上述三场景，不宣称所有训练家、完整通关或逐帧/音频等价。整份剧情模板是构造输入；只对已列宝可梦数据和场景断言负责，不声称整个模板自然可达。

原作 AI 第一版脚本错误地要求最终胜利，实际自然战斗以战败结束，因此没有计入最终6次；失败日志、已有原始画面与脚本保留。第二版接受实际结束结果并以普通 SAVE 读回图鉴。无效记录没有重标为通过。

最初 PR head `4d85225b` 的真实 GBA CI 因训练家更新 **235 ticks > 232.3** 失败。下载该 CI ROM 后，本地 mGBA 0.10.5 对七场景全部指标逐项复现；随后缓存方案仍为235/233，失败实测均保留。最终实际加载通知方案在相同 nightly、原始基线及阈值下连续两次通过七场景，训练家更新为 **232 ticks**。这只是本地性能门禁通过；新 head 的远程平台、GBA 内存及帧时序门禁仍须全部通过后才能合入。详见 `ci-performance.json`。

`verification.json` 为当前简明结论；归档中的 `audit-906-verification-current-events.json` 保存最新逐个 SRAM、检查点和哈希，历史 `audit-906-verification-full.json` 及原始记录保留。`evidence.zip` 对相同内容按 SHA256 去重，保留所有原始路径与原始字节；运行 `python3 extract_evidence.py evidence.zip --verify-only` 可独立校验。ROM/可执行文件不入库，精确哈希与构建源码清单保留；只在运行终结后删除冗余 ROM/可执行副本，原始状态、SRAM、输入、PNG、失败测量及本地引导/编译错误日志不删除。
