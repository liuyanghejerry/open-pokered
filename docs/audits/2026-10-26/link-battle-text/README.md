# 联机战斗末页提示的发布

基线为已合入黑雾修复的 master：`2115547503e702bf63ef79685c2c2caf2a9750e2`。

联机战斗中，确认输入可能在最后一页首次发布的同一帧将其清掉。例如后手使用“睡觉”时，双方都正确恢复 HP，但连续确认文字会跳过 `regained health!`，直接回到战斗菜单。

联机驱动器没有启用需要前端确认结束的招式动画，但应用仍会绘制它的战斗文字。原先这也关闭了文字首次发布的保护。本次让联机文字先发布，再允许输入确认；不增加招式动画等待。普通核心调用者关闭展示时的原有行为继续由既有测试覆盖。

## 复现和截图

新增回归使用两端实际 `LinkBattleDriver` 和 `ChannelTransport`，完成握手、请求/接受、队伍交换、开场和 FIGHT 选招，经过正常的远端招式交换执行回合。卡比兽使用睡觉，鲤鱼王使用跃起；用等级控制先后手，没有在开战后直接改写状态。检查双方的回复提示和 HP、睡觉使用者的本地 PP，以及两端一致的 RNG 状态。

[capture.rs](capture.rs) 驱动相同流程，再使用实际 `BattleVisualEffects` 和 `draw_battle` 绘制两端画面。双方交换招式后，各运行 81 次固定输入更新，在 10 个编号保存截图；两个先后手场景、两端合计 40 张。修复前后使用相同输入。

PR 展示后手睡觉的玩家端，更新编号为 64（从 0 计数）。基线已经回到战斗菜单；修复后可见回复提示，等待下一次确认。使用 Fusion Pixel 字体，没有绘制原作字体。

这是经过真实协议交换的核心驱动器与战斗渲染证据，不是完整 PokemonGame、网络传输、音频或原作时钟的逐帧证明。

## 最终验证

- 核心 3,799 项通过，1 项文档测试沿用忽略；应用 407 项通过，40 项沿用忽略。
- 新游戏到 m06 通过；11 项系统场景通过，包括独立进程保存和 CONTINUE。没有重跑 m01–m49 全主线。
- 未修改的 GBA 性能基线通过；mGBA 0.10.5 的 13 项内存压力场景通过，运行 323,040 帧，最低空闲堆 4,928 B，最低剩余栈 8,704 B。

内存验证首次在模拟器启动前遇到本地并行构建暂时移走历史可执行文件别名的问题。等待桌面构建恢复别名后，使用同一 ROM 和原检查器完成测试；没有修改游戏或放宽检查。
