# 图鉴／资料返回的计时交接

本次修复关闭图鉴或训练家资料时，同一个 native 更新被重复计时／执行音频工作。
基线为菜单背景修复 #453（`221cdd32`）；原作仍为 `pret/pokered@fbcf7d0e`，使用既有
常青市 SRAM 和只读原作准备状态，通过实际 START、选择菜单和 B 输入复现。

关闭菜单前，`update_native_clock` 已推进当前更新的计时和声音；随后立即接管的
恢复 IRQ 又执行了保留的旧 VBlank 请求。新增回归在两个菜单均复现预期 41、
实际 42 个计时单位。现在交接时确认这个已消费的 native 请求；不推进显示时钟，
不执行伪造的 IRQ／RETI，后续新 VBlank 仍按实际设备边沿处理。

## 实际结果与限制

| 观察 | 原作 | 修复前 | 修复后 |
| --- | --- | --- | --- |
| 取消的第一个更新，游戏时间增量 | 1 | 2 | 1 |
| 连续 40 次更新／原作帧，游戏时间增量 | 37 | 39 | 38 |
| 图鉴 START 输入读取／就绪 | t+14 | t+12 | t+12 |
| 资料 START 输入读取／就绪 | t+24 | t+23 | t+23 |
| 图鉴整帧白屏 | t+1～9 | t+1～8 | t+0～8 |
| 资料整帧白屏 | t+1～21 | t+1～19 | t+0～19 |

原作与 native 的进入过程、LCD 关闭期间的帧边界不同，40 帧计时仍差 1 个单位。
确认旧请求同时去掉了错误 IRQ 的耗时，因此 native 首个整帧白屏提前到 t+0，
仍不同于原作 t+1。**这只是重复工作修复，不是完整时序对齐**；没有用固定等待
补动画，也没有移动、抽取或插值录制帧。实际物理音频等价仍未验证。

桌面正常取消／恢复期间短按 Down 共四组，每组两遍 160 连续实际帧，前后各
1,280 帧。按键、坐标、SRAM、光标和重新打开同一菜单均通过；每组两次图像与
状态一致。逐帧前后比较仅 t+0 图像不同，后续 159 帧及最终完整画面相同。

默认 GBA 从普通 SRAM 冷启动、完整渲染与声音、无跳帧，四组输入各两遍 800
连续物理帧，前后各 6,400 帧。重复图像／按键一致，最终完整画面与基线相同，
重新打开菜单及读回 SRAM 检查通过。

另从石英高原 SRAM 冷启动，分别退出图鉴／资料后执行取消、短按、NO 长按、
YES 长按四种 SAVE 输入，各两遍，共 **16 次、23,200 个连续物理帧**。每次均
实际返回地图、重开 START，并在独立模拟器 CONTINUE；两遍图像、输入和 SRAM
一致，仅 YES 写档，没有分配失败。此项覆盖菜单衔接后的存档回归。

本地应用 `debug-server` 完整测试 **1,130 通过、92 忽略**；桌面和默认 GBA
构建、七组 GBA 性能门限、新开局到 m06（41.10 秒）通过。本轮没有以 m06
代替完整主线，也未跑 WASM 实机或物理音频等价验证。
