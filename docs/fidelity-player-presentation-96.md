# 普通玩家姿势与背景呈现（96）

本页属于草稿 PR #144；只证明以下实际输入场景，不代表所有场景、剧情或视觉均已对齐。

## 原作与夹具

原作固定为 pret/pokered `fbcf7d0e19a3a2db505440d3ccd3d40ca996c15c`。使用实际 SAVE 产生的 SRAM，经实际 CONTINUE 回到道路坐标 20,30；初始可见朝向 Down，最后停止方向 Left。骑车夹具由实际背包使用自行车准备。分别对 Left、Right、Up、Down 保持步行 32 / 骑车 16 个硬件帧，然后松键；连续录制 t=-1..99。原作、实际 master `31b1eda3112514d6bc803af559ec7f7c9e20374f`、修复后各录制两次，各自 PNG/JSON 字节一致。

初始整帧 RGB 的花朵动画相位不同；玩家前景和背景稳定区域一致。因此不声称整帧完全相同。真实 master 的场景时钟仍是 PR 之前的旧实现，前后截图体现整个 PR 的效果；969d1e3 上的额外缺陷核对与此项修复使用单独的连续帧记录。

## 缺陷和修复

969d1e3 的坐标、步行计数、最后停止方向与移动方向，在八种情况各 101 帧都与原作相同。但渲染器由单步 `walk_counter` 重算四段姿势，导致步行每个地块显示四次姿势，而原作的 `UpdatePlayerSprite` 每四次调用推进一次持久计数，跨地块延续。步行 Left/Right/Up/Down 分别有 18/20/24/20 帧姿势不同；骑车分别有 10/12/14/11 帧不同。

现在按原作调用位置更新精灵计数：正常开始移动在设置方向后、初始化步数前；持续移动在推进步数前；转向检查提前返回；松键的 NoDirection 在清除前次方向前更新。OAM 与 LCD 的呈现流水线保留两帧延迟，不按逻辑坐标即时重算姿势。

背景另行保存呈现视口。普通推进在下一次 vblank 显示，首次 LoadCurrentMapView 跨 vblank 时额外保持一帧。两者均由现有场景等待状态决定，未增加地图专用延迟，也未改变移动逻辑坐标或步数。骑车首次两次推进之间的重绘使用同一规则。

新增精灵计数、待显示姿势与背景视口均进入帧快照，并使用 serde 默认值兼容旧 JSON；SRAM 格式不变。脚本、连接、跳跃、推石和其他场景动画暂沿用各自呈现路径，仍需专项核对，不能据本页关闭这些审计项。

## 连续帧核对

使用原作 red / red_bike 图像的不透明像素识别姿势，排除透明区域的背景；有效调色对应黑、浅灰、白与透明。所有原作和修复后帧均可识别，八种情况各 101 帧的姿势差异全部为零。背景稳定区域 `(0,0,64,144)` 同帧 RGB 也全部一致。没有平移比对帧；历史“上一帧”比对仅作为诊断，未用于通过结论。

实际 master、原作及修复后的完整连续截图和状态记录在 `docs/screenshots/fidelity-player-presentation-96/raw-traces.zip`；manifest 含每个文件的 SHA256、提交和范围。展示截图选取步行 Down 的 t11，各表面保持相同物理输入和 SRAM。

由原作实际记录独立提取的姿势/镜头转换时刻固化为 `ordinary_player_pose_and_camera_match_original_hardware_frames`，逐帧验证八种情况各 100 帧。该专项通过；核心完整测试 3140 项通过，41 个结果组、1 个文档测试显式忽略，日志 `pose-96-final-core-all-tests.log`。新增的中途 JSON 快照重放在步行/骑车两种情况验证后续 90 帧完整快照一致，覆盖待显示姿势和视口。默认应用测试 497 项通过、52 项显式忽略；最终含 debug-server 的应用测试 507 项通过、54 项显式忽略，均为 39 个结果组，日志 `pose-96-app-all-tests.log` 与 `pose-96-final-app-debug-all-tests.log`。四方向推石及 3F 入洞连续画面复查，每种两次、201 帧全部 RGB 与原作一致；日志 `boulder-96-recheck-normal.log`。96 与 113 整合后的最后一次联合完整测试 `cargo test -p pokered-core -p pokered-app --features pokered-app/debug-server` 通过：核心 3140、应用 509，共 80 个结果组、55 项显式忽略、零失败，日志 `pose-96-113-final-core-app-tests.log`。最终二进制移动记录与上述归档字节完全一致；最终推石复核仍为十次各 201 帧 RGB 全部一致，日志 `boulder-96-113-final-recheck-normal.log`。最新提交完整 CI 及最终主线仍是合入前置条件。

## 骑车后打开 START 的站姿（113）

初版持久计数修复在骑车一格后进入 START 时冻结了踏步姿势。原作此时以 BIT_FONT_LOADED 清除计数，两帧 OAM/LCD 流水线后恢复站姿。实际原作和初版各两次 101 帧录制确认 86 帧姿势不同；步行同样的 START 持续输入没有暴露它。

现在从场景打开 START 时复位精灵计数，并在 UI 接管期间继续排空精灵呈现流水线；普通场景文字同样遵循计数清零规则。原作的场景字体分支仅在 walk_counter=0 时清零，移动中不套用这个规则。SRAM 与输入采样没有增加等待。

修复后骑车 Down、START 从 t5 保持 40 帧的实际 CONTINUE 录制，两次均与原作 101 帧玩家前景一致。真实输入自动回归同时覆盖步行和骑车：骑车菜单在 t12 开始，踏步保留 t12、t13，t14 恢复站姿；步行菜单在 t19 开始时已是站姿，直到 t99 都不再踏步。该回归在库与程序两个目标均通过。

`font-boundary/` 归档保留原作、真实 master、未修正字体计数转场的中间实现、最终修复四种连续记录；中间实现没有冒充 master。附加前后截图取实际 master 与修复后的相同 SRAM/输入 t20，原作截图也附在同目录。所有字体资产、字形样式和文字布局不在本项的差异通过结论中。
