# 用 AI 复刻《宝可梦 红》的五个月：进展、弯路与收获

**English version:** [Five Months Rebuilding Pokémon Red with AI: Progress, Detours, and Lessons](my-retro-2026-08.en.md)

2026 年 3 月，我开始用 AI 和 Rust 复刻《宝可梦 红》。我想看看，把任务从编程小练习换成一款完整的经典游戏，AI 到底能走多远。

五个月后，游戏已经可以玩了，支持 macOS、Windows、网页、Android 和 iOS，甚至还有终端界面（TUI）。我的目标是尽可能一比一还原原作的行为和画面，目前仍有部分动画和细节需要继续对齐。

![复刻版的城镇、对战、地图与开场画面](images/opening-screenshot-1.png)

*目前的复刻版：从真新镇出发，进入对战，也能打开地图、经历开场剧情。*

**[直接在浏览器里试玩](https://liuyanghejerry.github.io/open-pokered/) · [查看游戏源码](https://github.com/liuyanghejerry/open-pokered)**

这五个月里，我花了很多精力回答一个问题：AI 改完之后，我怎么知道它做对了？这个问题牵动了模型选择、调试工具、架构设计，也逐渐改变了我参与项目的方式。

这篇文章就讲这些变化，以及我至今还没解决的部分。

## 有原作代码，为什么还要做五个月？

社区的 [pret/pokered](https://github.com/pret/pokered) 已经提供了带注释的反汇编代码，我可以直接参考原作的实现。图像资源以原作为基础，游戏逻辑则用 Rust 重新实现，让它脱离 Game Boy 硬件运行。

但参考答案摆在面前，并不等于能直接翻译。原作有 1,923 个汇编文件、约 17.4 万行汇编代码，许多实现紧贴硬件，游戏逻辑与渲染也相互交织。换了语言、平台和架构之后，我需要重新确认这些实现的含义。

规模也是一个问题：151 只宝可梦、165 个技能、245 张地图，再加上训练师、NPC、道具和剧情事件。数值要对，触发条件要对，画面的变化过程也要对。自己设计游戏时，我可以决定规则；复刻时，原作的行为就是要核对的依据。

例如，一张对战截图看起来没问题，不代表捕捉时的随机数采样、剧毒状态的切换、暴击率查表都与原作一致。角色走到相同的位置，也不代表途中每一帧的移动节奏相同。

截至写作时，项目累计有 **1,823 条提交、189 次 PR 合并、41.6 万行代码**，统计范围包括游戏、引擎和工具链，涉及 Rust、Web、DSL 和 Python。这些数字可以说明工程规模，真正的还原程度还得靠逐项验证。

项目大致经历了四个阶段：

| 阶段 | 主要工作 | 随之出现的问题 |
| --- | --- | --- |
| 起步 | 从汇编中提取数据，建立模型和单元测试 | 测试通过，是否就忠于原作？ |
| 工具与引擎建设 | 拆分子系统，增加调试入口和脚本引擎 | 怎样让 AI 自己检查结果？ |
| 剧情与画面补全 | 批量迁移场景，比较截图和动画 | 怎样提高大量重复工作的效率？ |
| 完整试玩与收尾 | 跑通关流程，检查事件与细节 | 主线跑通之后，还漏了什么？ |

更详细的日期、工具和模型变化，可以查看[完整时间线](images/timeline.jpg)。下面按影响最大的几次变化展开。

## 模型变强之后，我能交出去的任务变大了

我对模型能力的判断，来自两种工作之间的落差。

写解析脚本、搬数据、迁移格式明确的场景，早期模型已经能做得不错。真正让我反复介入的，是那些需要判断两套实现是否等价的任务：左边是原作汇编，右边是我的 Rust，模型必须同时理解它们，再检查边界条件。

推理能力不足时，AI 会给出一份“看起来已经对齐”的报告。我仍然得重新检查关键行为。这类任务让我体会到，**模型能力决定了哪些判断可以交出去。**

移动端集成给我留下了很深的印象。早期模型在把 Rust 的帧缓冲渲染模块接入 Android、iOS 时，总是卡在生命周期和渲染集成问题上。后来换用 Claude Opus，同一个问题几乎在半小时内就打通了。这次经历直接影响了我后续的模型选择：遇到反复卡住的推理任务，我会更早尝试能力更强的模型。

视觉能力也改变了分工。字体阴影偏了一像素、菜单光标错位，以前需要我看截图，再把差异描述给 AI。像素对比能标出不同的位置，但解释差异、推动修复仍然离不开我。模型能直接分析截图之后，这部分工作才逐渐交了出去。

与此同时，承载模型、管理上下文并调用工具的编码代理环境——也就是常说的 **harness**——决定了这些能力能连续发挥多久。我先后用过四套主要工作环境：

| 工作环境 | 我能交给 AI 的任务 | 我的主要工作 |
| --- | --- | --- |
| Cursor / VS Code（三月） | 修改单个文件 | 审查每个 diff，组织提交 |
| opencode + OMO（三月下旬起） | 把一个功能分给规划、实现、评审等角色 | 拆任务，协调不同模型 |
| Claude Code（约五月底） | 连续推进一组相关改动 | 用项目说明和 skills 固化调试、验证流程 |
| kimi-code（八月下旬起） | 跨仓库查历史、追踪问题等长程任务 | 交代目标，检查依据与结果 |

OMO 的角色分工和上下文压缩，让一个功能有机会连续做完。后来，Claude Code 中的项目说明、skills 和更长的上下文，又让调试与截图验证变成可以反复执行的流程。到 kimi-code 时期，跨三个仓库做 git 历史追溯已经能成为日常任务，目标有时只需先交代到“把这件事弄清楚”。

从作者，到调度员，再到验收员，我的时间分配一直在变。过去需要我亲自拆开的任务，后来连拆分本身也能委派。但模型仍然需要明确的完成标准，以及检查结果的工具。

## 想让 AI 自己修好，先让它能检查

项目刚开始时，我让 AI 阅读汇编，为地图、宝可梦、技能、图鉴建立数据结构，并不断补充单元测试。

这里很容易产生一种错觉：测试都过了，实现就正确了。实际上，**测试只能检查它覆盖的情形；如果测试里的预期本身偏离原作，通过测试也不能说明复刻正确。**所以我还得让 AI 梳理原版的地图、对战等逻辑，再拿这些依据核对实现。

更麻烦的是，许多问题必须把游戏运行起来才能确认。

改完遇敌逻辑，要走进去触发战斗；检查一个训练师，要先走到他面前。我试过让 AI 只靠截图控制原版模拟器。它花了大量时间判断最基本的前进、后退操作，真正用于分析游戏的时间反而有限。

这让我开始建设专门的测试入口。对战是一个相对独立的子系统，我为它增加了命令行入口，让 AI 可以直接构造战斗、运行并读取结果。先检查算法，再补画面验证，省去了反复走剧情的等待。

后来，我参考 Chrome DevTools Protocol 的思路，给游戏做了一个调试服务器。它通过 TCP 接收命令、返回结构化数据，让 AI 可以直接操作游戏：

| 要验证什么 | 工具提供的能力 |
| --- | --- |
| 当前发生了什么 | 查询游戏状态、NPC 和剧情标记 |
| 指定地点的行为是否正确 | 直接传送到目标地图与坐标 |
| 一段操作会触发什么 | 批量发送按键序列 |
| 动画在哪一帧出现差异 | 同步逐帧推进并截图 |

5 月有了第一版调试入口，7 月又补上更适合试玩的控制能力、逐帧步进和无窗口运行模式。此后，战斗与画面还原的专项检查才更容易持续推进。

有了这些工具，定点逐帧比较就很有价值了：先把原作和复刻版带到对应场景，再比较相同操作下的画面变化。

单元测试之外，我还用画面快照测试记录菜单、对话框和战斗画面的输出。后续改动一旦改变这些基准画面，测试就会提醒我检查。它能防止已确认的结果悄悄变化，而画面是否忠于原作，仍要通过原版对照来确认。

这些检查逐渐进入 GitHub CI，通过 PR 自动运行。模型和工具一直在换，已经积累的验证能力则可以留下来。

最近，我又开始让 AI 编写操作脚本，模拟玩家完整通关。它能串起单独测试不容易覆盖的剧情关系，检查特殊道具和事件是否正确触发后续流程。

但试玩也暴露了自己的盲区：**不给额外引导时，AI 写出的通关脚本往往只走主线，很少探索支线。**一次顺利通关，不能代替对整个游戏的检查。遇到预期外的结果，也需要区分是游戏出了问题，还是脚本的操作和预期有误。

因此我开始在固定通关流程之外增加自由游走任务，接下来还需要专门扩大支线的探索范围。连续帧的理解、部分动效的还原，也仍然需要继续改进。

这些经历让我更愿意提前投入验证工具。每次增加一种状态查询或控制能力，后面的许多修复就能少依赖一次人工操作。

## 技术栈和架构，决定后续改动要付多少成本

项目第一周做出的技术选择，几个月后还在影响开发效率。

**Rust 对这个项目的一项重要价值，是降低验证成本。**编译器能在运行前发现类型、所有权和接口使用等问题，把反馈直接交给 AI。项目第 3 天就有 2,452 个测试在跑，它们和编译器一起，支撑了后续的大规模改动。

四月是唯一一个代码净减少的月份：新增约 4.8 万行，删除约 5.5 万行，期间包括编辑器重写和战斗系统重构。敢让 AI 做这样的改动，很大程度上是因为已有的检查能帮助我发现回归。

这让我在选语言时，更看重“机器检查产出的成本”。对这个项目而言，Rust 的编译期约束、测试能力和跨平台生态都发挥了作用。

但语言只能解决一部分问题。要继续加平台、改剧情、修画面，我还得为这些变化安排清楚的边界。

![open-pokered 的游戏、引擎与平台架构](images/open-pokered-architecture.png)

*工程按职责拆分：游戏规则与内容、可复用引擎、渲染和平台接入各有对应的位置。*

我主要做了三件事：

- **分开游戏与引擎。**把可以复用的能力抽出来，将宝可梦特有的规则和内容留在游戏侧，为以后开发其他游戏留出空间。
- **分开游戏逻辑与平台接入。**将窗口、硬件输入和具体显示方式隔离，让各端尽量复用核心逻辑。终端版也因此能接入已有的游戏能力。
- **分开内容描述与运行机制。**分别用领域专用语言（DSL）描述剧情和对话框布局，将适合的数据放进 JSON，让内容调整有统一入口，也支持开发时的热更新。

跨平台的结果来得很早：开工三天后，WASM 构建就跑通了；5 月拆分渲染器功能之后，Android 和 iOS 在月底跟上。平台适配仍然有生命周期和渲染集成等难题，但共享核心减少了重复实现，也降低了以后同步修改的负担。

内容与代码分离，则改变了剧情补全的方式。我起初担心，AI 会不会理解不了自己设计的 DSL。实际使用时，有了语法检查器和可随时查阅的手册，模型就能按规则编写场景。等脚本引擎稳定后，我开始用 Flash 系列模型批量补全剧情。

![用 DSL 描述主菜单布局并即时预览](images/editor-4.jpeg)

*布局编辑器把描述与结果放在一起：下面修改主菜单的 DSL，上面查看渲染效果。*

对话框也得到了类似的好处。过去散落在各处的布局，现在有了统一的表达方式，调整和核对都有明确入口。

随着代码和测试增多，架构边界还影响着回归成本。每次改动都跑全量测试，等待时间会越来越长。职责清楚的模块，让我更容易判断影响范围，安排相应的检查。

前期搭这些结构需要时间。到了后期，新平台、剧情补充和画面修复都有地方可改，这笔投入的收益才越来越明显。

## 模型便宜之后，更多工作值得去做了

项目规模变大之后，我开始更认真地考虑任务分工。

MiMo、DeepSeek 和 Kimi 等模型承担了相当一部分代码与内容产出，Opus 则继续处理复杂判断和评审。我的依据是任务要求：需要推理和语义核对的部分，用能力更强的模型；规则已经明确、可以自动检查的部分，交给成本更低的模型批量执行。

剧情迁移就是一个例子。脚本引擎、语法检查和参考手册准备好之后，大量场景都能沿着同一套规则处理。工具把单个任务约束得更清楚，模型成本的下降则让批量处理更容易承受。

逐场景比较、补充检查也有相似的变化。单项工作可能不复杂，但数量很大；过去会犹豫是否值得全部做，现在可以安排更多并行任务，再结合自动检查和更强模型的评审验收。

我保留了[月提交量与模型分工记录](images/monthly-commits.png)。提交数能帮助回顾工作节奏，但任务类型、提交粒度、模型和工具都在同时变化，不能单凭它计算某个模型带来的效率提升。

国产模型承担的工作越来越多，也让我有了更多选择。账号可用性、订阅成本和持续使用的便利程度，都是长期项目里需要考虑的实际问题。

对我而言，成本下降最直接的影响，是可以把更多原本舍不得反复做的检查纳入日常工作。

## 还没完成的部分，以及接下来要做什么

五个月之后，我已经能把更多实现、调试和验证工作交给 AI。我的精力逐渐集中到确定目标、设计边界，以及判断它提交的证据是否足够。

接下来仍有具体的工作要做：继续对齐动画时序，扩大支线与特殊事件的试玩覆盖，检查那些单张截图和一次主线通关都看不出来的问题。

模型能力的进步确实改变了这个项目。与此同时，每一个留下来的测试、调试命令和清晰的模块边界，也在帮助下一轮工作少走一点弯路。这是我现在更有信心继续做下去的原因。

游戏已经[开源](https://github.com/liuyanghejerry/open-pokered)，可以[在线试玩](https://liuyanghejerry.github.io/open-pokered/)。公开仓库是完成引擎拆分后的版本；抽出的引擎名为 [dotzuki](https://github.com/liuyanghejerry/dotzuki)，也有[在线体验入口](https://liuyanghejerry.github.io/dotzuki/stable/)。

如果你愿意试玩，尤其欢迎试试主线之外的角落。那些通关脚本很少去的地方，正是我接下来想继续检查的部分。
